# 집기 판정 보강 플랜

작성: 2026-11-09 14:53 KST. 쓰기 0건. 측정 입력은 `docs/261109-1444-집기-판정-임계값-사전측정.md`와 이 문서의 측정 표다.

## 목표

G0b 전에 집기 판정의 임계값을 측정값으로 고정하고, 밀리거나 떨어진 블록을 성공으로 세는 오류(R14)를 줄인다. 판정 기준은 G0b 시험 데이터를 보기 전에 커밋한다.

## 현재 상태 (As-Is)

- `make_pick_observer`는 사진 변화가 `PICK_CHANGE_MIN = 0.015` 이상이면 성공이다. 값은 측정 근거가 약하다.
- 블록이 보드에 그대로 있어도 밀려서 변화가 크면 성공이 되고, `has_block`이 참으로 남아 다음 시도가 빈 손으로 진행된다.
- 감독자 관찰을 시도 결과에 넣는 코드는 없다.
- `run_replay`는 마지막 시도가 성공하면 블록을 쥔 채 `park`에서 끝난다. 내려놓는 단계가 없다.
- 블록을 쥐고 `park`까지 간 적이 없다. 쥔 블록이 사진 어디에 보이는지 모른다.

## 접근 방법

| 안 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| 변화 임계값만 조정 | 코드 변경이 가장 작다 | 밀림·낙하 오판정이 그대로다 | 제외 |
| 시도마다 감독자 입력 | 사람이 직접 판정 | 30회 왕복, G0e 주기 90초와 충돌, 입력 경로 신설 | 제외 |
| 그리퍼 판독값 | 사진 불필요 | 물체 유무를 구분한다는 것이 아직 가정이다(G0e) | 제외 |
| **변화 + 보드 위 노란색** | 측정에서 깨끗이 갈린다, 사람 왕복 없음 | 보드 밖 낙하는 못 본다, 노란 블록 전용 | **채택** |

성공 조건은 **변화 ≥ 0.02 그리고 보드 안쪽 노란 화소 ≤ 100**이다. 두 값은 시도마다 기록한다.

## 시험 전 고정 규칙 (v2)

런북에 넣고 G0b 시작 전에 커밋한다. 결과를 본 뒤 바꾸지 않는다.

1. **낙하 규칙.** 자동 판정은 보드 밖 낙하를 알 수 없고, 낙하를 보기 전에 그 시도가 성공으로 기록될 수 있다. 그래서 **G0b 실행 중 감독자가 낙하를 1건이라도 관찰하면 집계 수치와 무관하게 그 실행은 미통과**로 기록한다. 런북대로 즉시 전원을 차단하고, 플랜 §6의 「구성 변경 후 1회 재시험」을 따른다. 기록을 고치거나 시도를 제외하지 않는다. 실패 경로의 `hover` 개방은 명령된 동작이라 낙하로 세지 않는다.
2. **재채점 금지.** 새 기준으로 이전 기록을 다시 채점하지 않는다.
3. **자료 구분.** `G0b-0`과 이번 사진, `G0b-1`은 교정 자료다. 승인 범위가 높이 선택이나 운반 확인이고 G0b 시험표를 쓰지 않는다. 판정값의 최종 고정 시점은 `G0b-1` 결과 반영 뒤, G0b 시작 전이다.

## 거짓 실패와 내려놓기 (v2)

- **거짓 실패**: 쥔 블록을 실패로 판정하면 기존 코드가 `hover`에서 연다. 약 40 mm 낙하가 될 수 있다. 실패로 세므로 합격 수치를 부풀리지는 않는다. `G0b-1`로 가능성을 줄이고, 이번에 코드를 바꾸지 않는다.
- **끝 내려놓기**: 현재 실행이 **정상 종료**하고 그 실행의 `has_block`이 참일 때만 수행한다. 예외, 쓰기 상한, 전원 차단에서는 자동 복구 이동을 하지 않는다.
- **미완료 처리**: 남은 시도가 없으면 재실행은 쓰기 없이 끝나므로 내려놓기를 잇지 못한다. 블록이 손에 있으면 사람이 받아 빼고 상태를 확인한 뒤, 별도 승인으로 진행한다.
- **재개 시 주의**: 재개하면 `has_block`은 거짓이고 `park`에서 개방한다. `--start-confirmed`는 **빈 그리퍼 확인**을 뜻하므로 블록을 쥔 채 재개하지 않는다. 런북에 명시한다.

## 변경

1. **`scripts/gemini_serve_core.py`**: `yellow_pixels(image, roi, min_sat=0.62)`를 추가한다. 측정에 쓴 식과 같게 `R>140, G>120, |R−G|<60, (R−B)/R>min_sat`이다.
2. **`scripts/gemini_serve.py`**: `{"op":"yellow","name":…,"roi":…}`를 추가한다. 입력 배열이 RGB인지 코드로 확인하고 맞춘다.
3. **`src/learned_grasp/camera.py`**: `Camera.yellow_pixels`, `FakeCamera`, `P620Camera`에 추가한다.
4. **`src/learned_grasp/session.py`**: `PICK_CHANGE_MIN = 0.02`, `PICK_BOARD_ROI = (585, 825, 190, 395)`, `PICK_YELLOW_MAX = 100`으로 두고 판정에 넣는다. `PICK_ROI`는 그대로 둔다. 위로 넓혀도 값이 나아지지 않았다.
5. **`src/learned_grasp/g0_runner.py`**: 위 조건에서 마지막 시도의 집기 자세에 내려놓고 `park`로 돌아간다. 시험표 집계에는 넣지 않는다.
6. **테스트**: 판정 조합, 노란 화소 100·101 경계, 변화 경계, 시도별 값 기록, 정상 종료 내려놓기, 예외 시 내려놓기 없음, 남은 시도 없는 재실행의 쓰기 0, 쓰기 수.
7. **문서**: 런북(쓰기 수 +5, 낙하 규칙, 재개 시 빈 그리퍼, 미완료 처리), `PROJECT-STATUS.md`.
8. **p620 사본 갱신**: `gemini_serve*.py`를 복사하고 실제 저장 사진으로 `yellow` 값을 재현한다.

값의 근거: 0.02는 남은 쪽 최댓값 0.0144와 떠난 쪽 최솟값 0.0256 사이다. 100은 빈 보드 최대 4와 블록 최소 447 사이다. **이 값은 후보이지 오판정률 검증이 아니다.** 정지 블록 사진의 분리일 뿐이고, 방향·가림·실제 파지 전후는 `G0b-1`에서 본다. `yellow_pixels`는 부호 없는 뺄셈 오버플로를 피하려고 실수로 계산한다.
