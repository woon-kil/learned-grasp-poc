# G0d 판정값 재계획 플랜

작성: 2026-11-10 10:08 KST. **v2**: 검토 반영. 의존 확인 절을 넣고, 운영 기준 사진 자세를 적고, 판정 건수를 28로 고치고, 운영 판정 함수를 그대로 돌리게 하고, 덮지 않는 띠를 범위 밖으로 적었다. 쓰기 0건 단계다. 계약 3 결과(`docs/261110-1002-G0d-윗면마커-계약3-결과.md`)가 **측정 합격, 판정 불합격**이라 계약 3의 64행대로 판정값을 다시 정한다. 측정 합격은 유지한다. 이 플랜이 승인되기 전에는 코드와 수치를 바꾸지 않는다.

## 목표

윗면 마커가 붙은 블록에서 G0d 집기 판정이 아래 두 가지를 모두 지키게 한다.

- 블록이 보드에 남으면(같은 자리, 돌림, 밀림, 가장자리) 성공이 하나도 없다.
- 블록이 떠나면 성공이다.

수치는 이 문서에서 고정하고, **새 계약 4의 새 사진**으로만 합격을 본다. 계약 3 사진은 원인 진단과 후보 산정에 썼으므로 합격 근거로 쓰지 않는다.

## 현재 상태 (As-Is)

- 판정 코드: `src/learned_grasp/session.py` 133~170행 `make_pick_observer`. 성공 조건은 `변화 ≥ 0.02` 그리고 `보드 노란 화소 ≤ 100`이다.
  - 변화 영역 `PICK_ROI = (540, 860, 190, 420)`
  - 노란색 영역 `PICK_BOARD_ROI = (585, 825, 190, 395)`
- 수치 근거(`docs/261109-1453-집기-판정-보강-플랜.md`):
  - 0.02는 남은 쪽 최대 0.0144와 떠난 쪽 최소 0.0256 사이다.
  - 100은 빈 보드 최대 4와 블록 최소 447 사이다.
  - 둘 다 **윗면 마커가 없는 블록**으로 잰 값이다.
- 계약 3 판정 결과: 45건 중 1건 불합격. `P1-removed-00`이 변화 0.0182, 노란 화소 0으로 거짓 실패였다.

## 원인 진단 (계약 3 사진, 쓰기 0건)

1. **P1 블록이 판정 영역 위쪽 경계(y=190)에 걸쳐 있다.** 블록의 노란 화소는 사진 전체에서 418이고, 보드 영역 안에서는 214다. 절반이 영역 밖이다. 겹쳐 그린 그림으로 확인했다.
2. **윗면 마커 블록은 치워도 변화가 작다.**
   - 변화 영역을 위로 넓혀도 P1 제거 변화는 0.0192(y 150부터), 0.0199(y 160부터)로, 0.02를 넘지 못한다.
   - P1에서 치움(0.0182)과 돌림(0.0179~0.0255)은 변화량만으로 갈리지 않는다. 계약 3에서 둘을 가른 것은 노란 화소다.
3. **E1은 노란 화소 106으로 문턱 100에 붙어 있었다.** 블록의 노란 화소는 사진에서 x 544~591에 있고, 보드 영역 왼쪽 경계 585 밖에 있다. 종이 왼쪽 가장자리는 x 550~570이라, 종이 위인데도 판정 영역 밖인 띠가 있다.
4. **운영과 관련된다.** G0d 셀 0은 r_index 1(124.04 mm)이다.
   - r − 단계는 r_index 0(119.75 mm)이고, 복귀 경로에서 블록을 이 자리에 놓는다(G0d 플랜 7단계).
   - G0c `c00`(r_index 0, J1 90)의 블록 노란 화소는 y 186~242에 있어 위쪽 경계에 걸친다.
   - 즉 P1처럼 경계에 걸친 배치는 G0d에서 실제로 생긴다.

## 접근 방법

| 안 | 내용 | 판단 |
| --- | --- | --- |
| A. 변화 문턱만 낮춤 | 0.02 → 0.01 | 위쪽 경계와 E1 문제는 그대로라 단독으로 쓰지 않는다 |
| B. 영역만 넓힘 | 노란색 영역을 위와 왼쪽으로 확장 | P1 변화 0.0192로 여전히 0.02 미만이다 |
| C. 윗면 마커 검출을 판정에 추가 | id 7이 보이면 실패 | 실행 경로인 p620 OpenCV 4.5.4가 id 7을 59/64만 잡았다. 서버 변경과 버전 문제가 생겨 이번에 넣지 않는다 |
| **D. A + B** | 노란색을 주 판정으로, 변화는 「아무 일도 없었다」를 거르는 보조로 | **채택** |

D의 역할 분담은 다음과 같다. **운영에서는 노란색이 사실상 단독 판별이다.**

- 운영 기준 사진은 `run_replay`가 `_place` 직후에 찍는다(`g0_runner.py` 255행).
- `_place`는 `park`에서 끝나므로(157~162행), 기준 사진은 그리퍼를 연 `park`이고 판정 사진은 그리퍼를 닫은 `park`다.
- 사전 측정의 「블록이 남은 경우」 변화는 0.0039~0.0144였다(`docs/261109-1444-…` 16행). 그래서 0.01 문턱은 블록이 남은 운영 실패를 일부만 거른다.
- 남은 블록은 노란색이 막는다. 계약 4는 손 배치라 그리퍼 차이가 없으므로, 변화 항의 운영 역할은 시험하지 못한다.

- **노란 화소:** 「블록이 보드에 있다」를 판정한다. 계약 3에서 남은 경우 44건은 모두 ≥ 106, 제거 2건은 0이었다.
- **변화:** 장면에 블록 제거만 한 변화가 없으면 실패가 되게 하는 보조 조건이다.
  - 문턱은 「움직이지 않은 장면의 잡음 + 블록 아닌 물체 변화」보다 위, 「블록 제거」보다 아래로 둔다.
  - 블록이 움직였는지는 노란색이 본다.
  - 0.02를 그대로 두면 운영에서도 제거가 거짓 실패가 될 수 있다. 계약 3 P1의 0.0182가 그 예다. 그래서 낮춘다.

## 새 수치 (실행 전 고정)

| 항목 | 기존 | 새 값 | 근거 |
| --- | --- | --- | --- |
| 변화 문턱 `PICK_CHANGE_MIN` | 0.02 | **0.01** | 아래 근거 1 |
| 변화 영역 `PICK_ROI` | (540, 860, 190, 420) | 그대로 | 넓혀도 P1 제거 변화가 0.0182 → 0.0192로 거의 같고, 영역 변경은 의존 검증 범위만 늘린다 |
| 노란색 영역 `PICK_BOARD_ROI` | (585, 825, 190, 395) 1개 | **(585, 825, 150, 395)와 (565, 585, 250, 395) 2개의 합** | 아래 근거 2 |
| 노란 화소 문턱 `PICK_YELLOW_MAX` | 100 | 100 그대로 | 새 영역에서 빈 보드 0~4, 쥔 블록 운반 사진 최대 52, 계약 3 남은 블록 최소 415(기존 영역에서는 106) |

**근거 1. 변화 0.01**

- 움직이지 않은 장면은 0.0001~0.0005다. 사전 측정 문서와 계약 3의 같은 자리 18쌍에서 잰 값이다.
- 블록이 아닌 변화(분홍 메모가 틀어짐)는 0.007이었다.
- 블록 제거의 최솟값은 0.0182다(계약 3 P1). 기존 사전 측정의 제거는 0.0256 이상이고, G0b·G0c 실제 집기 60건은 0.0373 이상이다.
- 0.01은 0.007과 0.0182 사이에 있다.
- 기존 「남은 쪽 최대 0.0144」는 블록이 움직였다가 남은 경우다. 이제 이 경우는 변화가 아니라 노란색이 막는다.

**근거 2. 노란색 영역 2개**

- **R1 (585, 825, 150, 395):** 위쪽을 y 150까지 넓힌다.
  - 빈 보드는 0, 0, 4화소다(P1·P3 제거 사진, 계약 3 시작 사진).
  - 블록을 쥔 채 `park`에서 찍은 G0b·G0c 집기 뒤 사진 60장에서 최대 52화소로, 기존 영역과 같다.
- **R2 (565, 585, 250, 395):** 종이 왼쪽 띠다.
  - 종이 왼쪽 가장자리는 빈 보드 사진의 밝기 단차로 쟀다. y 200에서 약 570, 250에서 약 565, 300에서 약 560, 350에서 약 555, 390에서 약 550이다.
  - y 250 아래만 쓰고 x 565부터 시작해 나무가 들어오지 않게 한다.
  - 운반 사진 60장 최대 0, 빈 보드 0, 0, 0이다. E1 블록은 R2에서 453화소다.
- **바꾸지 않는 부분:** 오른쪽 띠(825~835)와 아래쪽 띠는 그대로 둔다. 계약 3 E2·E3가 584·870화소로 충분했다.

G0b·G0c 사진은 G0b·G0c 판정을 다시 매기는 데 쓰지 않는다. 쥔 블록이 새 영역에서 거짓 실패를 만들지 않는지 보는 데만 쓴다. 거짓 실패는 `hover` 자동 개방(D4)으로 블록을 떨어뜨리므로 따로 본다. 단, 그 사진의 블록에는 윗면 마커가 없었다. 윗면 마커가 붙은 블록을 쥐고 찍은 사진은 `G0d-0`에서 처음 본다(G0d 플랜 리스크 표 198행).

## 계약 4 (판정만, 새 사진)

판정 부분만 새로 본다. 측정 항목(윗면 마커 검출, 돌림 구분, 위치)은 계약 3 합격을 유지한다. 카메라, 마커, 배치, 측정 코드가 바뀌면 측정도 다시 본다(계약 3 64행).

- **도구:** `scripts/marker_precheck4.py`. 계약 3의 미리보기, 버전 고정, 경로 거부, 완결 로그를 그대로 쓴다. 판정은 `session.py`의 판정 함수와 같은 식을 import해서 쓰고, 별도 사본을 두지 않는다.
- **자리:** 놓는 자리는 SVG 그림으로 제시한다(AGENTS 문서 규칙).

| 자리 | 위치 | 사진 |
| --- | --- | --- |
| N | 블록 베이스 쪽 끝을 베이스 판 가장자리에 거의 닿게 (r_index 0보다 가깝게) | 놓음 3, 돌림 +1, 돌림 −1, 밀림 1, 치움 1 |
| P1 | 계약 3과 같은 자리 | 같음 |
| M | 보드 마커 바로 베이스 쪽, 마커는 보이게 (G0d 셀 1 부근) | 같음 |
| P3 | 보드 마커를 덮게 (G0d 셀 2 부근) | 같음 |
| E1, E2, E3 | 계약 3과 같은 정의 | 각 1, P1 놓음 사진 대비 |
| E4 | 종이 왼쪽 가장자리 가운데, 전부 종이 위 | 1, P1 놓음 사진 대비 |

- **사진 수:** 4자리 × 7 + 4 = 32장이다.
- **비교 방식:** 판정은 각 자리 첫 놓음 사진과 나머지를 비교한다.
  - 자리마다 같은 자리 2, 돌림 2, 밀림 1, 치움 1로 6건씩, 4자리에서 24건이다. E1~E4 4건을 더해 **판정은 28건**이다.
  - 같은 자리, 돌림, 밀림, E는 **성공이 하나라도 나오면 불합격**이다.
  - 치움 4장은 **모두 성공**이어야 한다.
- **판정 실행:** 도구가 식을 다시 조립하지 않는다.
  - 저장 사진을 읽는 카메라 어댑터를 만들어 운영 `make_pick_observer`를 그대로 돌린다.
  - 어댑터의 `change`와 `yellow_pixels`는 `gemini_serve_core`를 쓰고, BGR을 RGB로 바꾼다.
  - `analyze --dir` 기본값은 `<out>/frames`로 둔다.
- **유효 조건:**
  - 미리보기에서 N·P1·M은 보드 마커가 보이고 P3는 안 보여야 한다.
  - 바깥 기준 마커 id 0, 1이 전 사진에서 2화소 안에 있어야 한다.
  - E는 `y` 확인을 받는다.
  - 무효면 계약을 끝내고 새 계약으로 간다.
- **불합격 처리:** 이 수치를 결과에 맞춰 바꾸지 않는다. 원인을 기록하고 새 플랜으로 간다. C안(마커 검출)이나 셀 위치를 바꾸는 안을 그때 검토한다.

- 계약 3의 측정 합격은 판정 코드와 무관해 그대로 유효하다.

## 범위 밖

- G0d 시험표, 오프셋 단계, 합격선, 집계를 바꾸지 않는다.
- G0b·G0c 결과를 다시 매기지 않는다.
- 윗면 마커 검출을 판정에 넣는 안(C)은 이번에 하지 않는다.
- 노란색 영역이 덮지 않는 곳은 범위 밖이다. 이곳에 남은 블록은 자동 판정이 보지 못하고, 감독자와 묶음 뒤 사진 대조가 본다.
  - 왼쪽 위 띠(x 565~585, y 150~250)
  - 종이 오른쪽 띠(x 825~835)
  - 종이 아래쪽 띠(y 395~400)

  G0d 셀은 J1 90 줄이고 블록이 x 686~723 부근에 놓인다(G0c `c00`). 밀린 블록이 이 띠까지 가는 경우만 해당한다.
- 보드 밖 낙하는 이번에도 자동 판정으로 보지 못한다. 감독자와 묶음 뒤 사진 대조가 본다(G0d 플랜 70행).
