# DB-2 DaBai 깊이 결측 원인 분리 — 실기 승인 요청 (초안)

작성: 2026-11-10 KST. 실행 전 기록이다. **지금은 승인 전이고 팔에 명령을 보내지 않았다.** 앞선 결과는 `docs/261110-1638-DB-1-DaBai-작업거리-측정-결과.md`, 승인 절차는 `docs/261110-1634-DB-1-승인-내역.md`와 같다.

## 1. 목적

DB-1에서 `grasp`(모델상 렌즈 축 거리 약 122~129 mm)의 DaBai 깊이가 전부 결측(0)이었다. 원인 후보는 ① 너무 가까움 ② 내가 DB-1에서 **`enable_ir:=false`** 로 띄워 IR 자동 노출이 꺼짐 ③ 기타(반사 등)다. Yahboom 소스는 `enable_ir`을 기본 `true`로 둔다(`data/refs/yahboom/src/ros1-orin-nano/OrbbecSDK_ROS/launch/dabai_dcw2.launch`, 커밋 안 함, Jetson `dabai_dcw2.launch.py` 확인). 이 한 세션으로 ②가 원인인지 가린다. 판정 게이트가 아니고 사실 기록이다.

## 2. 가설과 변형

| 변형 | 런치 인자(기본 위에 덧붙임) | 보려는 것 |
| --- | --- | --- |
| C0 | `enable_ir:=false` | DB-1과 같다. **이미 측정함**, 재측정하지 않는다 |
| **C1** | `enable_ir:=true` | IR을 켰을 때 `hover`·`grasp` 깊이 유효 비율 |
| **C2** | `enable_ir:=true depth_registration:=true` | 정합 설정이 깊이 영상 크기·화각·유효 비율을 바꾸는가 |

- park 자세 사전 확인(쓰기 없음): C1·C2 모두 `/dabai/depth/image_raw` 640×400, 화각 92.6°×66.4°로 나왔고 프레임률은 같았다. 정합이 이 토픽에 반영되는지는 park 자세에서 구분되지 않았다. `grasp`에서 처음 본다.
- 결론 기준(사전 고정): `grasp` 중앙 영역 깊이 유효 비율이 C1에서 0보다 크면 DB-1의 결측에는 `enable_ir:=false`가 기여했다고 적는다. C1도 0이면 IR이 원인이 아니라고 적고 최소 거리·반사는 미분리로 남긴다. 수치 합격선은 없다.
- 분석 정의는 DB-1과 같다(전체 640×400, 중앙 열 160~479·행 100~299, 유효는 깊이 > 0, p05·중앙값·p95).

사용자에게 받을 것(DB-1과 같다): 시작 확인(빈 그리퍼, `park`, 경로에 물체 없음, 블록·마커 블록을 보드와 DaBai 시야 밖으로 치움), 그리퍼 서보 시작 온도, 끝 온도와 이동 중 관찰.

## 4. 하지 않는 것

- 닫기, 블록 집기, 다른 r_index·J1·J5, 표 변경, 새 전이.
- 기대 깊이값을 사용자에게 알리지 않는다.
- 줄자 높이 측정(DB-1과 같은 이유로 제외).
- 이 결과로 L3(DaBai 보정) 채택 여부를 결정하지 않는다.

## 5. 위험

DB-1과 같은 세션이고 새 전이도 새 코드도 없다. 바뀐 것은 대기 중 드라이버 재시작뿐이다. Jetson 메모리는 DB-1에서 약 1.6 GB 사용(총 7.6 GB)이었다. 드라이버를 세션 전에 한 번 확인하고(`pgrep`), 재시작마다 `stop`으로 내린 뒤 다음을 띄운다. 이전 드라이버가 남아 새 드라이버가 못 뜨는 문제는 DB-1 정정(`component_container` 잔존)에서 고쳤다.

## 6. 승인 후 순서

1. 사용자 답변 「승인, 시작 확인, 그리퍼 ○○도」를 받아 `runs/DB-2/approval.json`과 승인 내역을 만들고 실행 전에 커밋한다.
2. `load_approval` 검증, 시작 전 관절 조회, Jetson 프로세스 확인.
3. `session dabai-view`를 백그라운드로 띄우고 Monitor로 도착 줄을 기다린다. 도착마다 C1 → C2를 촬영하고 신호 파일을 쓴다.
4. 드라이버를 내리고 종료 후 조회, 결과 문서와 `PROJECT-STATUS.md`를 갱신한다.
